# 설정 기반 머신비전 검사 프로그램

주어진 `.ini` 규격을 해석해 패턴별 촬상과 검사를 수행하는 프로그램을 C++로 구현하고,
촬상과 검사를 병렬화해 **검사 시간을 18.21초에서 10.06초로 단축**했습니다.

| | |
|---|---|
| 기간 | 2025.07 ~ 2025.09 |
| 환경 | C++ / Visual Studio / Windows |
| 형태 | 개인 과제 (컴퓨터비전 연구실 학부연구생) |

## 저장소 구성

| 폴더 | 내용 | 검사 시간 |
|---|---|---|
| `MachineVision(ver1)Code` | 촬상과 검사를 직렬로 수행 | 18.21초 |
| `MachineVision(ver2)Code` | 생산자·소비자 구조로 병렬화 | 10.06초 |

구조 변경 전후를 비교할 수 있도록 두 버전을 모두 남겨두었습니다.

---

## 요구 사항

설정 파일에 촬상 패턴 3종과 검사 알고리즘 5종이 정의됩니다.
각 알고리즘은 자신이 사용할 패턴을 지정하며,
프로그램은 이를 해석해 패턴을 순서대로 촬상하고
해당 패턴을 쓰는 알고리즘만 선별해 수행해야 합니다.

```ini
[general]
total pattern count=3
total algorithm count=5

[pattern00]
pattern name=red
shutter speed=1

[pattern01]
pattern name=green
shutter speed=3

[pattern02]
pattern name=blue
shutter speed=2

[algorithm00]
algorithm name=scratch
pattern=red,green,blue

[algorithm02]
algorithm name=red defect
pattern=red
```

`scratch`와 `stain`은 세 패턴 모두에서 수행되고,
`red defect`은 red 패턴에서만 수행됩니다.

---

## 구현

### 1. 설정 해석과 방어 로직

섹션과 키를 읽어 패턴·알고리즘 정보를 저장하고,
`pattern=red,green,blue` 형태의 문자열을 분리해 대응 관계를 구성했습니다.

패턴 수나 이름이 비어 있으면 `false`를 반환해 **검사를 아예 시작하지 않도록** 막았습니다.
잘못된 설정으로 장비를 동작시키는 것보다 멈추는 편이 안전하다고 판단했습니다.

### 2. 책임 분리

데이터, 장비 제어, 흐름 제어를 네 개 클래스로 나눠 설계했습니다.
패턴과 알고리즘 정보를 담는 데이터 클래스,
카메라 연결·파라미터 설정·촬상을 담당하는 제어 클래스,
그리고 설정 로드부터 검사 순서 제어와 결과 출력까지 맡는 흐름 제어 클래스로 구성됩니다.

### 3. 처리 구조 개선 — 18.21초에서 10.06초로

ver1은 촬상과 검사를 직렬로 수행했습니다.
단계별 시간 점유를 정리해보니 **카메라가 촬상하는 구간 내내 연산 자원이 대기**하고 있었습니다.
서로 다른 장치가 순차로 기다릴 이유가 없다고 보고 구조를 바꿨습니다.

- 카메라를 생산자, 검사 알고리즘을 소비자로 두고 큐로 연결
- 카메라 제어 명령도 큐로 처리해 메인 스레드가 멈추지 않도록 함
- 큐 접근 락과 카운터 보호 락을 분리해 경합 구간을 축소

### 4. 병렬화가 실제로 되고 있는지 재검증

여기서 끝내지 않고 스레드별 점유를 다시 확인했더니,
**워커를 여러 개 띄웠음에도 하나의 워커가 모든 알고리즘을 순차 실행**하고 있었습니다.
큐에 담기는 단위를 알고리즘 기준으로 바꿔 실제 병렬 처리가 이뤄지도록 수정했습니다.

종료 처리도 함께 손봤습니다.
대기 중인 작업을 비우고 연결 해제를 예약한 뒤 모든 스레드를 정리했고,
소멸자에서는 카메라 연결 상태를 확인해 연결돼 있을 때만 해제하도록 했습니다.

---

## 결과

검사 시간이 18.21초에서 10.06초로 약 45% 줄었습니다.

이론적 하한은 셔터 스피드 합(1 + 3 + 2 = 6초)에
패턴 전환 시 파라미터 설정 시간을 더한 값입니다.
더 줄이려면 파라미터 설정과 촬상을 겹치거나 카메라를 늘려야 합니다.

---

## 배운 점

해결했다고 믿은 지점을 다시 확인해 오류를 찾아낸 경험이 가장 컸습니다.
스레드를 나눴다는 사실만으로 병렬 처리가 되는 것이 아니라,
작업을 어떤 단위로 쪼개 큐에 넣느냐가 실제 동작을 결정한다는 것을 확인했습니다.

성능 개선은 숫자가 줄었다고 끝나는 것이 아니라,
의도한 방식으로 줄어든 것인지 검증해야 완결된다고 생각하게 됐습니다.
